# Judge 通用评审执行

## Why

Issue #10 补齐真实执行入口：调用方提供确定的规则、代码等证据和执行配置，一次调用获得可追溯的逐项意见、完成状态与把关说明。现有配置偏向模型，无法诚实表达程序检查；现有执行记录也不能表达实际请求与响应声明的区别。

## What Changes

- 增加通用公开评审入口，默认执行一次；调用方可明确指定顺序重复次数。
- 支持调用方提供的程序检查函数，以及首个 OpenAI Chat Completions 兼容非流式文本 provider。
- 版本化演进评审定义、评审方法、完整测量和执行记录；保留冻结 rubric 的来源、适用范围和参考项语义。
- 默认兼容约定的 JSON 外层代码块；逐项校验并展示合法的部分发现，不把不完整结果包装成完整测量。
- 接通 #9 的聚合、校准适用性和用户说明，区分质量结论、执行完整性与自动把关资格。
- 提供仅消费公开入口的离线示例、接入文档和实施交接 prompt。

## Scope and Non-goals

#10 实现评审。产品还包括基于代码与已有意见给出修改建议、经用户授权实际修改代码；这两类由 #11 实现。#10 保留可供后续消费的意见、理由、证据、来源及完成状态，不建立空 workflow 能力。

不做自动采集或启动测试、规则草案生成、逐项混合执行、自动重试、自动修补模型答案、结果缓存、CLI、流式、多模态、工具调用、远端执行认证或 benchmark 迁移。代码块兼容属于读取，不是修复。未来修复功能必须由用户明确选择。
